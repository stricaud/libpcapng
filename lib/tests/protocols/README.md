# Protocol conformance specs

One file per protocol. Each describes some bytes and what they must decode to,
and `protocol-conformance` checks every one of them on every build. This is
what a release is held to: not "the library still runs", but "the decoders
still say the same, correct thing about the same bytes".

    ctest -R Protocol-Conformance
    ./lib/tests/protocol-conformance             # all specs, verbose
    ./lib/tests/protocol-conformance dns         # one, by file stem
    ./lib/tests/protocol-conformance --write DIR # also write each as pcapng

`../captures/` holds a committed pcapng per spec, regenerated by `--write`.
They are there to be opened in Wireshark — which is the cheapest way to check
that a packet is what the spec claims, using an implementation that is not
this one.

## Adding a protocol

Twelve lines, no C:

    name     Modbus/TCP read holding registers
    packet   tcp 10.0.0.1:45000 > 10.0.0.2:502  0001 0000 0006 01 03 0000 0001
    proto    Modbus/TCP
    info~    READ_HOLDING_REGISTERS
    field    ModbusTCP.function_code   3
    label~   ModbusTCP.function_code   READ_HOLDING_REGISTERS
    absent   ModbusTCP.byte_count

`pcapsh` will tell you what a packet actually offers, which is the quickest way
to find the field names:

    $ pcapsh
    > rdpcap("lib/tests/captures/dns.pcapng")
    > rdpcap("lib/tests/captures/dns.pcapng", "dns.qname")

### Directives

| | |
|---|---|
| `name TEXT` | what the spec is about, printed as the heading |
| `linktype ethernet\|raw` | default ethernet |
| `packet ...` | starts a packet; everything after it applies to that packet |
| `proto NAME` | `d->proto` exactly |
| `info TEXT` / `info~ TEXT` | `d->info` exactly / contains |
| `field ABBREV N` | numeric value; `0x` accepted |
| `str ABBREV TEXT` / `str~ ABBREV TEXT` | string value exactly / contains |
| `label~ ABBREV TEXT` | the rendered label contains TEXT — how to check an enum name |
| `present ABBREV` / `absent ABBREV` | the field is / is not in the tree |
| `xfail REASON` | the *next* check is known-broken; see below |

### Packet forms

    tcp SRC:PORT > DST:PORT  HEX      Ethernet/IPv4/TCP, PSH|ACK
    udp SRC:PORT > DST:PORT  HEX      Ethernet/IPv4/UDP
    ip4 SRC > DST proto N    HEX      Ethernet/IPv4, raw IP protocol
    eth 0xTYPE               HEX      Ethernet, raw ethertype

Hex may be grouped with spaces, colons or dashes — group it the way the
protocol's own fields are laid out, so a reader can see the structure.

## Where the expected values come from

This matters more than anything else here.

Recording whatever the decoder currently prints produces a test that describes
today's behaviour, bugs and all. It will notice a change, but it cannot tell
you the change was wrong — and it will defend a bug against being fixed.

So the values in these files are read off the protocol's specification and the
packet's own bytes. `dns.qname` is `www.example.com` because the bytes spell
`03 'www' 07 'example' 03 'com' 00`, not because the decoder said so. Where a
value records what the decoder does rather than what the field means, the spec
says so in a comment — `ntp.precision` is one: it is a signed exponent that the
decoder reads as unsigned, and the spec notes that fixing that should change
the expected value.

## xfail

A check whose expectation is right and whose decoder is wrong is marked
`xfail`, with the reason:

    xfail    syslog.facility is documented and colour-ruled but never derived
    field    syslog.facility   4

The expectation stays honest, the failure does not turn a release red for a
defect already known — and if the decoder is ever fixed, the check passes
unexpectedly and *that* fails the run, because the marker has outlived its
reason and should be deleted. A known bug is either tracked or forgotten, and
this is how it stays tracked.
